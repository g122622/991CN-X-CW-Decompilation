# Ghidra 反编译结果的已知缺陷与处理方式

本工程以 `原始反编译结果/991CN X.ghidra原始.c` 为输入。该文本**不参与编译**，
所有缺陷都在生成阶段（`toolchain/parse.py`、`build_project.py`、`rawasm.py`）处理，
原始文件保持原样以便溯源。下面按缺陷类型列出表现、影响与处理。

## 1. 函数被过度简化

| 表现 | 例子 | 处理 |
|------|------|------|
| 整个函数只剩 `return;` | `FUN_rom_009d22`（ENTER）、`FUN_rom_009d2a`（LEAVE） | 这两个是裸汇编的帧指针辅助，Ghidra 无法表达“改 SP/ER14”的副作用；命名库按真实语义说明，生成时对 `0x0000`/`0x93FE` 也做了等价的语义重写 |
| 跨块共享的栈帧被拆成片段 | 大量函数的尾部块以 `unaff_ER14` 读调用者栈 | 生成时统一改名为 `fp` 并在头注释注明其来自调用者 |
| 前导块与完整函数重叠 | `0x82EC` / `0x82F6` | 保留两个入口，注释说明重叠关系 |

## 2. 函数边界错误（花括号问题）

**处理策略：不修补，交给解析器容忍。** Ghidra 在以下情况会写出花括号不平衡的文本：

- 函数体内出现子入口的声明（`0x1F12E`、`0x22006`、`0x23BD6` 之后）；
- 字符常量 `'\x7f'` 吞掉了内层 `}`（应为 `'{'`）。

`parse.header_at_top()` 只在花括号深度为 0 处认函数声明，因此被并入前一函数的子入口
不会破坏后面的切分；`build_project.load_records()` 在生成前对所有函数体做一次
平衡检查，**不平衡就中止并列出地址**（`函数体花括号不平衡: ...`），不做任何自动修补。
当前 1311 个函数体全部通过该检查。被并入前一函数的子入口在 `src/` 中以 `@addr`
注释保留。

> 仍有个别函数把 Ghidra 的“子入口注释/声明”写进了函数体尾部（见
> `tests/check_split.py` 的 `moved-comment tails` 统计，当前为 0）；一旦再次出现，
> 检查脚本会报出来，而不是悄悄改动原文。

## 3. 指令被写窄/写残

`991CN X.汇编.txt` 中三类情况（逐字节核对得到，见
[`casio-main符号对照.md`](casio-main符号对照.md) §5）：

| 类型 | 例子 | 影响 | 处理 |
|------|------|------|------|
| 4 字节指令只写了首字节 | `0xD85E` 的 `01`（实为 `01 F2 82 2B`） | 反汇编地址补充脚本会错位 | `rawasm.fix_width()` 用参考反汇编补齐 |
| 2 字节写完后，高字节另起 `??` 行 | `0x92C8` 的 `08 E3` + `50 92` | 同上 | 同上，并丢弃被覆盖的残行 |
| 指令与其后紧邻的标签并成 `addr` 行 | `0xD84C`、`0xD860` | 旧版 `align.asm_numbered` 把残片当成函数体起点 | 已改为只认 4 字节指令行 |

## 4. 数据被当作代码、代码被当作数据

- 参考反汇编（`_disas_commented.txt`）的方向扫描与本工程（Ghidra 控制流）各有盲区；
  两者逐字节比对后，**参考 59988 条中 59914 条一致（99.88%）**，其余 74 条全部可解释
  （向量表字节序、方向扫描误判的 `RTI`、Ghidra 合并 4 字节指令等）。
- `0x000..0x200` 是向量表兼数据区，Ghidra 把 `0x200` 起的一段当成函数 `bad_entry`；
  该名字保留但标注为“无效入口”。
- ROM 末尾 `0x3FF40` 之后是数据/填充，Ghidra 把 `0x3F3F4`、`0x3F8F3` 识别为函数，
  对齐时记为 `tail_asm`（只出现在汇编、没有对应的 C 函数）。

## 5. 原文中的手工改名

`991CN X.ghidra原始.c` 曾被人工插入注释与调用名（如把 0x94DA 的调用点写成 `delay(...)`）。
这些“活名”不属于 Ghidra 输出：

- 函数声明处的活名（如 0x94DA 声明为 `delay`）由 `build_project.OLD_ACTIVE_NAMES` 还原；
- 调用点处的活名按同一张表映射回真实函数；
- 记录见 [`casio-main符号对照.md`](casio-main符号对照.md) §7。

## 6. 类型系统

Ghidra 输出的类型几乎全是 `undefined` / `undefined2 / undefined4 / byte *` 的组合，
没有结构体。生成阶段做的处理：

- 返回值被使用而原型为 `void` 的，放宽为 `int`（205 个）；
- 调用点实参少于原型的补 `(uintptr_t)0` 占位；
- `unaff_*` 寄存器变量统一改名为 `in_*` / `fp`；
- 全局变量按 `naming_db.GLOBALS` 换成语义名。

因此 `checkscan.py`（clang 语法/类型扫描）仍会报约 1000 条类型错误，主要是
“把数值当函数调用”“参数个数不符”——这些是原始反编译的类型缺口，不代表切分错误。
判断切分是否正确应看 `tests/check_split.py`（地址、尾部注释）与
`tests/check_asm_parity.py`（字节覆盖）。
